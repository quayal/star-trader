# Execution plan: E02-S01 — create a game

Source doc: .ai/specs/2026-10-25-e02-s01-create-game.md
Issue: #19

## Goal

A signed-in player can create a new game with a chosen length in turns
(`POST /api/games`) and becomes its first player. The game is stored under its own id,
separate from every other game (R01), and waits in the lobby.

## Scope

- New `game` package: domain (`Game`, `GameStatus`, `Player`, `GameIdGenerator`,
  `GameStore`, `GameCreationService`, `InvalidGameOperationException`), adapters
  (`memory`, `random`, `web`) and tests.
- The controller resolves the caller through `login.SessionStore`, the same way
  `GET /api/login/session` does.

## Non-goals

- Joining (E02-S02), persistence (E02-S03), polling (E02-S04), the start step, the
  create/lobby screens and starting resources (E02-S05).
- Any change to `trading` or `trading.Player`.
- Requiring a session on any existing endpoint.

## Decisions and deviations from the spec, recorded

The spec's 2026-10-29 header says E02-S05 wins where they differ. Applied:

- **Request body.** `POST /api/games` takes `{ "turns": N }` (E02-S05 criterion 3).
  `N` must be a whole number from 1 to 50 (criterion 1's proposed bounds). The rule
  lives in `GameCreationService` (business rules in the domain service, not the
  controller); a missing or out-of-range value is `400` with E02-S05's message
  "Enter a whole number of turns from 1 to 50."
- **Response.** Adds `turns`, `status` (`LOBBY` at creation; the enum also has
  `RUNNING` and `FINISHED` for E02-S05/E05) and `creatorEmail`.
- **No money or ships at create.** E02-S05 moves 300 HT, 2 ships and placement to the
  start step, so `game.Player` carries only `email`, `name` and `corporationName`. The
  spec's `Ship` type and the Q2/Q3 placeholder constants are dropped; E02-S05 adds
  ships when it places them. This also removes the spec's reuse of `trading.StarSystem`.
- **`Game.addPlayer` and `GameStore.update` stay** as the spec describes (max 6 players,
  no duplicate email; atomic per-id update), so E02-S02 needs no port change.
- **Controller test signs in by storing a session** through the `SessionStore` bean
  rather than running the email-code flow; that flow is already covered by
  `LoginControllerTest`, and this test is about `/api/games`.

## Implementation Plan

### Phase 1: Domain

- 1.1 `Player`, `GameStatus`, `Game` (with `addPlayer`) and `InvalidGameOperationException`, with `GameTest`.
- 1.2 `GameIdGenerator` and `GameStore` ports with fakes; `GameCreationService` with `GameCreationServiceTest`.

### Phase 2: Adapters

- 2.1 `InMemoryGameStore` and `RandomGameIdGenerator`, with adapter tests.
- 2.2 `GameController` (`POST /api/games`) and DTOs, with `GameControllerTest`.

### Phase 3: Gate

- 3.1 `./gradlew build` green; docs touched only where they describe the API's consumers.

## Risks

- Placeholder bounds (1–50 turns) are E02-S05's proposed defaults; one constant to change.
- In-memory store loses games on restart until E02-S03.
