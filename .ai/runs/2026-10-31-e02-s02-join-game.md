# Execution plan: E02-S02 — join a game

Source doc: .ai/specs/2026-10-25-e02-s02-join-game.md
Issue: #20

## Goal

A signed-in player can join a game that is still in the lobby
(`POST /api/games/{id}/join`) and is added to its players. An unknown game, a full
game, a game that has started, or a player already in the game is refused.

## Scope

- `game` domain: `Game.addPlayer` also refuses a game that is no longer `LOBBY`; a new
  `GameNotFoundException` and `GameJoiningService` (find the game, then add the player
  through the atomic `GameStore.update`).
- `game` web adapter: the join endpoint on `GameController`, with tests.
- `BACKWARD_COMPATIBILITY.md` §6: the new row.

## Non-goals

- Starting resources and ship placement, the start endpoint, and the lobby screens
  (E02-S05, #35).
- Persistence (E02-S03, #21) and reading a game back (E02-S04, #23).
- Any change to `GameStore`, `InMemoryGameStore`, `trading` or `login`.

## Decisions and deviations from the spec, recorded

The spec's 2026-10-29 header and the `om-backlog` note on #20 say E02-S05 wins where
they differ. Applied:

- **No money or ships on join.** `game.Player` has none since E02-S01; the spec's R22
  "same starting resources" wording is dropped. Resources come at the start step.
- **Joining a started game is refused with `409` "This game has already started"**
  (E02-S05 criterion 9). `GameStatus` already exists on `main`, so the rule goes in now,
  inside `Game.addPlayer` with the other join rules. No game can reach `RUNNING`
  through the API until E02-S05, so the controller test seeds one through `GameStore`.
- **Messages match E02-S05's state table:** `404` "This game doesn't exist", `409`
  "This game is full" / "This game has already started". The already-a-member case keeps
  E02-S01's "This player is already in the game" (the lobby only offers Join to
  non-members, so players never see it).
- **A domain service decides 404 vs 409.** `GameJoiningService.joinGame` throws
  `GameNotFoundException` for an unknown id and lets `InvalidGameOperationException`
  through for the rest; the controller only maps them to statuses (business rules in the
  domain service, not the controller). It calls `find` before `update`; games are never
  deleted, so the game can't vanish between the two.
- **Spec step 4 (concurrent-join test on `InMemoryGameStore`) already exists:**
  E02-S01 added `InMemoryGameStoreTest.shouldApplyConcurrentUpdatesOneAtATime`, which adds
  five players from separate threads and checks all land. Not duplicated.
