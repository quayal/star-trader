# Execution plan: E05-S08 — The game ends after the last turn and shows the winner

Source doc: .ai/specs/2026-10-29-e05-trading-phase.md
Issue: #53
Stacked on: E05-S07 (#52, PR #93, branch `feat/e05-s07-turn-ends`)

## Goal

When the last turn's Trading has resolved its last good, the game ends and no further turn starts (S08-1). The last
turn is the creator's chosen length (R39, R41: `Game.turns`, 1–50, default 20 in the create form), not a fixed 20.
Every player is taken to s09 "Game over": each player's final money, highest first, and the winner, by cash alone
(S08-2). Final money is shown to everyone, the one exception to R29 (S08-3). Players tied on money share the win
(S08-4). The log ends with "Game over: {winner} wins with {money} HT" (S08-5). After that every action is gone, and
the board, system screens and log stay readable (S08-6).

## What already works (checked before planning)

- E05-S07 (PR #93, this branch's base): `Game.endTurn(current)` is the one place a turn ends. After `turns` it sets
  `GameStatus.FINISHED`, keeps the last turn and logs "All goods resolved".
- `Game.runningTurn()` refuses every action on a finished game with "This game is over" (409), so S08-6's server side
  holds already. On the client, every form and button is gated on `status === 'RUNNING'` or on a Trading/Bidding
  helper that checks it.
- `turnText` already says "Turn n of N · Game over" for a finished game, and "Your games" lists it as "Finished".
- Game length: `Game.turns` is stored on the game item and sent as `turns`.

## Scope

- **Domain** (`game`): `Game.standings()` (money, most first; join order breaks ties) and `Game.winners()` (everyone
  with the most money). `endTurn` adds "Game over: … wins with 2,310 HT" after the last turn's "All goods resolved".
- **Web**: `GameResponseDto.result` `{ standings: [{ email, corporationName, money }], winners: [email] }`, set only
  for a finished game (R29 until then).
- **Frontend**: `js/game-over.js` (winner text, standings rows, money with thousands separators, `gameJustEnded`); the
  route `#game/{id}/game-over` (s09) with a sidebar link shown once the game is over; every player is taken there
  when the game ends, like Trading's start (S01-1); s03 says "All goods resolved. The game is over."

## Non-goals

- Valuing ships or goods (R39: cash only). Warehouses, factories and loans (N08, N05).
- E05-S06's last-turn position rolls (see Decisions).

## Decisions (autonomous, reversible)

- **The result is a separate `result` field, null until the game is over**, instead of adding money to
  `players[]`. That way `players[]` never carries money, and the R29 exception is one field that tests check is null
  while the game runs.
- **Places are shared on a tie** ("1, 1, 3"), and tied winners are named in standings order (join order among
  equals): "Vega Lines and Kessler Cargo win with 300 HT"; three or more read "A, B and C win with …".
- **Money is written with thousands separators** in the log and on s09 ("2,310 HT"), as in S08-4's example. The top
  bar's "Money: 300 HT" is unchanged.
- **s09 is its own screen** (`#game/{id}/game-over`) rather than a panel on the Deck. Players are taken there once, at
  the moment the game ends, so the Deck, System details, Trading and the log stay readable afterwards (S08-6). On a
  game that isn't over, it says so instead of showing anyone's money.
- **For the creator: E05-S06 (PR #94) still rolls positions on the last turn**, and logs "… from turn {last + 1}", a
  turn that never comes. This run doesn't change S06. It's a spec question whether the last turn should skip those
  rolls, or still roll them without the "from turn" part.

## Implementation Plan

### Phase 1: Domain

1. `Game.standings`, `Game.winners`, the game-over log line. Tests: `GameOverTest` (the end, ranking by cash, the log
   line, a three-way tie, thousands separators, every action refused).

### Phase 2: Adapters

1. `GameResultResponseDto` / `StandingResponseDto`, `GameResponseDto.result`. Tests: `GameResponseDtoTest` (null
   while running, the same for every viewer once over, tied winners), `GameControllerTest` (a one-turn game over HTTP).
   `BACKWARD_COMPATIBILITY.md` §6.

### Phase 3: Frontend

1. `js/game-over.js` with tests; the `game-over` route in `js/game.js`; s03's game-over status in `js/trading.js`.
2. s09 in `index.html`: panel, sidebar link, the move there when the game ends.

### Phase 4: Verify

1. Full gate, then a browser walk with three players in a one-turn game: the last trade ends the game, both open
   pages go to s09, a shared win, every screen without actions afterwards, the log's last line, phone width.

## Risks

- R29: `result` must stay null until the game is over. Checked in `GameResponseDtoTest`.
- S07's `GameTurnEndTest.shouldNotStartAnotherTurnAfterTheLastOne` checked that the log's last line was "All goods
  resolved". It now checks that the line is there and no turn 2 starts, since the game-over line follows it.
