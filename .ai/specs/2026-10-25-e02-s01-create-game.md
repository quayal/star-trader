# E02-S01 — A player can create a new game and becomes its first player

> **Update 2026-10-29 (brief R40–R42):** starting resources and ship placement changed. Players get 300 HT and 2 ships of 10 bulky units each, and ships are placed at random Ports in different systems **when the creator starts the game** (E02-S05), not when a player creates or joins. Creating a game also takes a length in turns (R41). Read `2026-10-29-e02-s05-create-join-start-game.md` alongside this spec; where they differ, E02-S05 wins.

## 📝 TLDR

No game/room concept exists anywhere in the codebase today — `TradeOfferBook` is a single global, unscoped list, which is why the README's "many groups playing simultaneously" claim doesn't hold up (R01). This spec adds the first slice of the fix: a signed-in player can create a new game, becomes its first player with a starting money balance and 3 ships (R22), and the game's state is isolated from every other game (R01). It does not add joining (E02-S02), real persistence (E02-S03), or state polling (E02-S04) — each is tracked separately and builds on what this spec introduces.

## 📝 Problem Statement

`TradeOfferBook`/`TradeOfferController` hold one global list with no notion of "which game" an offer belongs to. `[PRODUCT]` `src/main/kotlin/dev/adriangrzebyk/trader/trading/TradeOfferBook.kt`, `src/main/kotlin/dev/adriangrzebyk/trader/trading/adapter/web/TradeOfferController.kt`. R01 requires "a single deployment hosts many concurrent, independent games; all state and identity are scoped per game" — nothing today creates or scopes a game at all. This is also the first story to depend on E01-S02's session (#14): without an authenticated caller, there is no one to attribute game creation to.

## 📝 Proposed Solution

A new `game` package (by game concept, per `.ai/engineering-standards.md` §1) exposes `POST /api/games`. A new domain service creates a `Game` aggregate with a generated id, the creating (session-identified) caller as its first player with a starting money balance and 3 fixed-capacity ships (R22, pending Q06's exact numbers — see Resolved assumptions), and stores it behind a `GameStore` port. `GameController` resolves the caller's identity from the `Authorization: Bearer <token>` header via E01-S02's `SessionStore` port — the same session mechanism E01-S02 built, reused here rather than re-authenticating some other way.

Alternative considered: letting the caller supply their own name/corporation/email in the request body, independent of their session. Rejected — E01-S02 already resolves that identity from the session token; asking for it again would let a caller create a game under an identity that isn't theirs, directly undermining D03's purpose ("the server knows this request really is player X").

Alternative considered: reusing the existing `trading.Player` class (it already has `money`, `reputation`, `positions`) for the new per-game player record. Rejected, named explicitly here rather than silently done: `trading.Player` has no stable id, no ships, and is a technical-layer leftover from before any game/room concept existed — extending it would mean `game` reaching into `trading`'s internals for a concept (player identity + resources, scoped to a game) that belongs to `game`, not `trading`, per engineering standards §1. A new `game.Player` is introduced instead; see Risks & Impact Review for the resulting (named, not hidden) duplication with `trading.Player` until a later epic reconciles them.

## 📝 Architecture

New package `dev.adriangrzebyk.trader.game`, mirroring `trading`'s and `login`'s shape (domain at the top, adapters in `game/adapter/*`). This is the foundation E02-S02/S03/S04 all build on without re-deriving it:

- `Ship` — domain value: `data class Ship(val cargoCapacity: Int, val currentSystem: StarSystem)`. Reuses `trading.StarSystem` as shared domain vocabulary (the six star systems are fixed universe geometry, not trading-specific business logic — not a reach into `trading`'s internals).
- `Player` (the new `game.Player`, distinct from `trading.Player` — see Risks) — `data class Player(val email: String, val name: String, val corporationName: String, val money: Int, val ships: List<Ship>)`.
- `Game` — `data class Game(val id: String, val players: List<Player>)`, plus a domain method `fun addPlayer(player: Player): Game` enforcing E02-S02's invariants (max 6 players, no duplicate email) — added now as a pure function on the aggregate so E02-S02 has somewhere to put that logic without reopening this story; unused by this story's own endpoint, which only ever creates a game with one player.
- `GameIdGenerator` (port) — `fun generate(): String`; real adapter `adapter/random/RandomGameIdGenerator` (`UUID.randomUUID().toString()`, mirrors `login`'s `RandomSessionTokenGenerator`); fake for domain tests.
- `GameStore` (port) — `fun create(game: Game)`, `fun find(id: String): Game?`, `fun update(id: String, mutate: (Game) -> Game): Game` (atomic read-mutate-write per engineering standards §9 — see below). Real adapter `adapter/memory/InMemoryGameStore` for this story (mirrors `login`'s `InMemoryOneTimeCodeStore`); swapped for a real persistent adapter by E02-S03 once E02-S03-T01 picks a store — no port change expected, per that story's own spec. Fake for domain tests.
- `GameCreationService` — domain service (plain class, not a Spring bean, mirrors `LoginCodeRequestService`/`CodeExchangeService`): `fun createGame(creator: Player): Game` generates an id, builds a `Game` with `creator` as its sole player, stores it via `GameStore.create`, returns it.
- `adapter/web/GameController` — `@RestController`, `POST /api/games`. Resolves the caller via `Authorization: Bearer <token>` → `login.SessionStore.find(token)` (a legitimate cross-package dependency: `login` is the identity authority every other package resolves "who is calling" through, not a reach into its internals — it's the same public port E01-S02 itself exposes via `GET /api/login/session`). A missing/unknown token → `401`. On success, builds the creator's starting `game.Player` from the resolved session (email, name, corporationName) plus the starting-resources constants (see Data Model), calls `GameCreationService.createGame`, returns `201 Created` with the new game's id and player list.

`GameStore.update`'s atomicity (engineering standards §9 — "a single atomic/idempotent operation, never a read-decide-write split") matters starting with E02-S02's join, not this story (which only ever calls `create` once per request, no concurrent-mutation hazard) — it is specified here because `GameStore` is this story's port, and E02-S02 must not have to change its shape to get it.

## 📝 Data Model

- `Game`: `id` (opaque random string, no join-code concept — see Resolved assumptions), `players` (list, exactly one after this story's own endpoint runs).
- `Player` (game-scoped): `email` (the membership key — see Resolved assumptions on Q01), `name`, `corporationName` (both captured from the session at creation time, not re-entered), `money` (starting balance, a placeholder constant — Q06 open), `ships` (exactly 3, each with a placeholder cargo-capacity constant and the same default starting system — Q06/location both open, see Resolved assumptions).
- Storage: in-memory only (`ConcurrentHashMap<String, Game>` in `InMemoryGameStore`), unbounded, no persistence — consistent with `login`'s own stores today, pending E02-S03/D02. A server restart loses every game created by this story alone; that is this story's own named, expected gap, closed by E02-S03.
- No sensitive-data concern beyond what E01-S02 already handles (email/name are already captured and scoped by the session); this story adds no new confidential field (R02's confidential half still has nothing to carry at this point in the backlog, same note E02-S04's spec will make).

## 📝 API Contracts

`POST /api/games`

Request: no body — everything needed (the creator's identity) comes from the `Authorization: Bearer <token>` header.

Response: `201 Created` —

```json
{
  "id": "3f1c...e2",
  "players": [
    { "email": "adrian@example.com", "name": "Adrian", "corporationName": "Adrian Star Traders", "money": 500, "ships": [{ "cargoCapacity": 10, "currentSystem": "GAMMA_LEPORIS" }, ...] }
  ]
}
```

Failure: `401 Unauthorized` — missing, malformed, or unknown bearer token (mirrors `GET /api/login/session`'s own convention from E01-S02, so this is not a new error-handling pattern).

## 📝 Edge Cases & Failure Scenarios

- No `Authorization` header, or a token that doesn't resolve to a session → `401`, no game created (AC2).
- A signed-in player creates a second game → allowed; nothing in R01/this story's scope limits one player to one game, and Q01 is explicitly non-blocking. Each call creates an independent, separately-scoped game.
- Server restart after a game is created by this story alone → the game is lost (in-memory only); explicitly not this story's problem (E02-S03 owns it), not a silent gap.

## 📝 Risks & Impact Review

- **A second, now-competing `Player` type exists (`game.Player` alongside the pre-existing `trading.Player`).** Named here, not hidden: `trading.Player` (with its `reputation`/`loan`/`positions` fields the brief already calls "unused" for MVU per N05) has no id, no ships, and was never scoped to a game or persisted anywhere real. This story does not touch or remove it — reconciling the two (or retiring `trading.Player` in favor of `game.Player`) is a decision for whichever later epic (E05, Trading phase and resolution) actually needs trading actions to update a *persisted, game-scoped* player's money and market position; forcing that reconciliation into this story would block game creation on a trading-domain decision this story has no need to make.
- **In-memory-only storage means every game created by this story is lost on restart.** Intentional and temporary, exactly like `login`'s own placeholder stores — E02-S03 (already filed, #21) replaces `InMemoryGameStore`'s role in production; no port change anticipated.
- No existing contract is touched — `/api/games` is wholly new surface.
- `GameStore.update`'s atomicity contract is specified now but has no caller yet in this story; it exists so E02-S02 doesn't need a port change to use it correctly, per engineering standards §4 (build the port's full needed shape before piling fixes onto it later) weighed against §5 (no speculative abstraction) — it tips toward specifying it now because the alternative (E02-S02 redesigning this port under schedule pressure) is the worse failure mode for a port other stories already depend on existing.

## 📝 Decisions in play

- R01 — a deployment hosts many concurrent, independent games; all state and identity are scoped per game (owner: creator). This story creates the first scoped game.
- R22 — each player starts with a fixed money balance and exactly 3 ships of predetermined cargo capacity; no purchasing/commissioning for v1 (owner: creator). Implemented with placeholder numbers pending Q06.
- D03 — login is passwordless; this story is the first consumer of E01-S02's session outside the `login` package itself.
