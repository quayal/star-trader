# E02-S02 — A player can join an existing game as another player

## 📝 TLDR

E02-S01 (#19) lets a player create a game but the game can only ever have the one player who created it — nothing lets a second player in. This adds `POST /api/games/{id}/join`: a signed-in player joins an existing game with fewer than 6 players, becoming an additional player with the same starting resources as everyone else (R22). A full game, an unknown game, or a player already in the game are all rejected.

## 📝 Problem Statement

E02-S01 introduced `Game`/`Player`/`GameStore` and the one endpoint that creates a single-player game. R01 and the brief's own Target group ("small group, 2–6") require more than one player per game, and nothing today adds a second. `[PRODUCT]` `game/Game.kt`, `game/adapter/web/GameController.kt` (on E02-S01's branch).

## 📝 Proposed Solution

Add `POST /api/games/{id}/join` to the existing `GameController`. It resolves the caller's identity the same way `POST /api/games` already does (session token → `login.SessionStore`), builds a starting `game.Player` the same way E02-S01's create endpoint does, and calls `GameStore.update(id) { it.addPlayer(player) }` — the atomic mutator E02-S01's spec already put on `Game`/`GameStore` for exactly this purpose, so this story needs no port change.

Alternative considered: a read-then-write (`find`, mutate in the service, `create`/overwrite) instead of `GameStore.update`. Rejected — two players joining the same game at nearly the same instant would race (engineering standards §9); `update`'s atomic mutator, already specified by E02-S01, is what avoids that without this story inventing new port surface.

## 📝 Architecture

No new package, no new port. Extends `GameController` with one endpoint, and exercises `Game.addPlayer` (added by E02-S01, unused there) for the first time:

- `Game.addPlayer(player): Game` (already defined in E02-S01) throws `InvalidGameOperationException` (already defined in E02-S01) when the game already has 6 players, or already has a player with that email.
- `GameController`'s new endpoint: resolves the caller exactly as the create endpoint does (`401` on a missing/unknown token); loads/validates the target game exists (`404` if `GameStore.find(id)` is `null`); calls `GameStore.update(id) { it.addPlayer(newPlayer) }`, translating `InvalidGameOperationException` to `409 Conflict` (a new status for this app — see Risks & Impact Review); returns `200 OK` with the updated `GameView` on success.

## 📝 Data Model

No schema change beyond what E02-S01 defined. A joining player gets the same starting-resources constants as the creator (same placeholder money/ship values, same Resolved-assumptions caveat pending Q06).

## 📝 API Contracts

`POST /api/games/{id}/join`

Request: no body — `Authorization: Bearer <token>` identifies the joining player, `{id}` in the path names the game.

Response: `200 OK` — the updated `GameView` (same shape E02-S01's `201` returns), now listing the new player among `players`.

Failure:
- `401 Unauthorized` — missing/unknown token (same convention as E02-S01's create endpoint and E01-S02's exchange/session endpoints).
- `404 Not Found` — no game exists with `{id}`.
- `409 Conflict` — the game already has 6 players, or the caller's email is already a member of it.

## 📝 Edge Cases & Failure Scenarios

- A game with 5 players, a 6th joins → succeeds, now full (AC1).
- A game already at 6 players, a 7th attempts to join → `409`, roster unchanged (AC2).
- A nonexistent game id → `404` (AC3).
- A player already in the game attempts to join again → `409` — not spelled out in the issue's three ACs, but directly implied: without this check, re-POSTing join would either silently no-op or duplicate the player's entry, neither of which is sensible, and `Game.addPlayer`'s own duplicate-email check (specified by E02-S01) already covers it for free.
- Two players joining the same game at nearly the same instant → both succeed if the game has room for both, because `GameStore.update`'s mutator runs atomically per game id (engineering standards §9); neither overwrites the other's join.

## 📝 Risks & Impact Review

- **Introduces `409 Conflict`, a new status for this app** (previously `400`/`401` only). Deliberate: a full game or an already-joined player is a state conflict, not a malformed request (`400`) or an authentication failure (`401`) — `409` is the standard, correct signal and this app's own convention of "pick the status that actually matches the failure kind" (set by E01-S02's introduction of `401`) extends naturally here.
- No change to E02-S01's existing `POST /api/games` contract or response shape — purely additive.
- Relies entirely on `GameStore.update`'s atomicity, which E02-S01 specified but never exercised; this story is the first real proof that contract holds. If E02-S01's in-memory adapter's `update` is not actually implemented atomically (e.g., a naive `find` + `create` pair instead of a synchronized `compute`), this story's concurrent-join test will catch it — called out so the implementer treats that test as load-bearing, not incidental.

## 📝 Decisions in play

- R01 — all state and identity scoped per game; this story is what actually makes a game have more than one identity in it.
- R22 — the joining player's starting resources are identical to every other player's.

## 📋 Implementation Plan

### Phase 1 — Join an existing game

1. Add `game/GameCreationServiceTest.kt`-adjacent coverage is not needed here (no new service); instead add `game/GameTest.kt` (plain JUnit, domain-only, per engineering standards §7) directly against `Game.addPlayer`: a 5-player game accepts a 6th; a 6-player game rejects a 7th (`InvalidGameOperationException`); a game already containing an email rejects a second join with that email.
2. Extend `game/adapter/web/GameController.kt` with `POST /api/games/{id}/join`: resolve caller (`401`), `GameStore.find(id)` (`404` if null), `GameStore.update(id) { it.addPlayer(newPlayer) }` catching `InvalidGameOperationException` → `409`, else `200` + `GameView`.
3. Extend `game/adapter/web/GameControllerTest.kt`: create a game, join it with a second session's token → `200` with 2 players; join a nonexistent game id → `404`; join the same game twice with the same session → second call `409`; fill a game to 6 players then attempt a 7th → `409`.
4. Add a concurrency test exercising `InMemoryGameStore.update` directly (plain JUnit, no Spring): fire two `update` calls for the same game id from separate threads, each adding a different player, and assert both land (the store's roster ends up with both players, not one overwriting the other) — the proof that engineering standards §9's atomicity requirement actually holds for this port's real adapter.
5. Run `./gradlew build` as the gate.
