# Backward compatibility

What this project treats as a protected contract surface, and how a change to one must be handled. Review skills check changes against this file; implementation skills warn when a change isn't compliant.

## Context: this is a pre-launch, single-maintainer project

Per `.ai/specs/product-brief.md`, there are no real players or external clients yet, and the current API is explicitly **expected** to be replaced as multi-game hosting (R01), authentication (D03) and persistence (D02) land. Treat the surfaces below as "don't break without noticing", not "frozen forever" — but still require every breaking change to be a deliberate, stated decision (ideally recorded in the product brief's Decisions table), not an accident.

## Protected surfaces today

### 1. Game rules (highest protection)

`StarSystem`, `Goods`, `OfferType`, `SupplyDemand` (once `SDCalculator`), and the resolution logic in `game/Resolution` (with `Offer`, `Trade`, `Wholesale`, `PositionRoll`), which is what a game's Trading runs, encode the original board game's actual rules; so do `TradeDesk` / `BestOfferCalculator` / `DiceRoller`, the first attempt's resolution, which no game uses any more. Together they encode those rules (business rule R03: six star systems, four tradable goods, dice-resolved trades). These are the closest thing this project has to a stable contract, because they're fixed by the board game itself, not by this codebase's current stage.

- **Breaking change**: altering a star system's name/goods, a good's identity, the dice mechanic, or the offer-matching/pricing logic in a way that changes a game outcome for the same inputs.
- **Required path**: must come with a test proving the new behavior against the original game's rule, and a note in the PR body explaining why the rule changed (new house rule, bug fix against the original, etc.) — not silently "while I was in there."

### 2. HTTP API — `/api/options` (`TradeOfferController`)

| Method | Path | Request | Response |
|---|---|---|---|
| GET | `/options` | — | `TradeOfferOptions` (star systems with their fixed market, offer types, price bounds) |

- Consumers: the home "Market Overview" in `static/index.html` and `static/design-system.html`.
- **Breaking change**: removing/renaming a field in `TradeOfferOptions`, `StarSystemOption` or `GoodsMarket`; changing a field's type or meaning; removing the endpoint.
- **Required path**: update both consumers in the same PR and call the change out in the PR body.
- **Removed in E03-S03**: the unscoped `GET /trade-offers` (listed every player's offers to anyone, against R17/A05), `POST /trade-offers` (no game, no session) and `GET /trade-offers/resolve`, with `static/trade-offers.html`, their only consumer. Offers are placed per game with `POST /api/games/{id}/offers` (§6), the replacement this section anticipated.

### 3. Login and session — `/api/login/*` (`LoginController`)

The passwordless login flow (D03). The sign-in screens (E01-S03) and every later endpoint that needs to know "this request is player X" depend on it.

| Method | Path | Request | Response |
|---|---|---|---|
| POST | `/login/request-code` | `{ playerName, corporationName, email }` | `202`, or `400` for a blank name or malformed email |
| POST | `/login/exchange-code` | `{ email, code }` | `200` + `{ sessionToken }`; `400` for a blank field; `401` for a wrong, expired, reused or never-requested code, or once the code's 5 attempts are used up |
| GET | `/login/session` | `Authorization: Bearer <sessionToken>` | `200` + `{ playerName, corporationName, email }`; `401` for a missing, malformed or unknown token |

- **Session lifecycle**: a session token is an opaque string and never expires (D05); sessions are stored in the games table (§7) and survive a server restart, so a token kept in the browser stays valid (2026-11-02). A one-time code is valid for 10 minutes and for at most 5 attempts, and is used up by a successful exchange.
- **Breaking change**: renaming or removing a field above; changing a status code; changing how the token is sent (bearer header → cookie, say); giving sessions an expiry; letting a `401` reveal *which* reason applied.
- **In-repo consumers**: `static/sign-in.html` (request and exchange the code) and `static/js/session.js` (keeps the token in `localStorage` as `starTrader.sessionToken` and checks it with `GET /login/session` on every game screen). The sign-in screen maps E01-S01's 400 messages to its fields by their exact text (`static/js/sign-in.js`), so rewording one of those messages must update that map too.
- **Required path**: update the in-repo consumers above in the same PR, and state the change in the PR body's "Decisions touched". Session expiry would also need a superseding entry for D05.

### 4. Frontend/backend contract

`src/main/resources/static/index.html` is served as-is by Spring Boot's static resource handling and talks to `/api/*`. A change to the API response shape or the static file's expectations of it must keep both sides in sync within one PR — there is no versioning or feature-detection between them today.

### 5. Build and tooling contract

- `./gradlew build` is what CI (`.github/workflows/*.yml`) and this repo's validation gate (`SDLC.md`) run; it must keep working from a clean checkout with JDK 17.
- The frontend's JavaScript unit tests (`jsTest`, part of `check`) need Node 22+ on the PATH. CI installs it and never skips them; a local checkout without `node` skips them with a warning, so JDK 17 alone still builds.
- ktlint style rules (`build.gradle.kts`) are enforced as part of `check`; a change to `.editorconfig`/ktlint config that relaxes a rule project-wide is a deliberate decision, not a drive-by fix for one file.

When Bidding closes, every player's money goes down by their bid (all-pay, R27), `turn.initiative` lists every player's playerId in initiative order (public, empty during Bidding) and `log` gains "Initiative order (bid + d2): {corporation} → …", without amounts (E03-S05). `turn.turnOrder` is this turn's turn order (public, R26): one entry per place, first to last, each the playerId of the player who picked it or null while free. It's empty during Bidding and has one entry per player from Ship-jumps on; players pick in initiative order, so whose pick it is is the first `turn.initiative` playerId not yet in `turnOrder`. Each pick adds "{corporation} chose 2nd" to `log`, the last player's "{corporation} gets 3rd, the only place left", then "Turn order (for this turn): {corporation} → …" (E04-S01). Once the order is set, players jump in turn order (E04-S02): whose slot it is is the first `turn.turnOrder` playerId not in `turn.doneJumping`; `turn.jumpedShips` names the ships that jumped this turn (each jumps at most once) and `turn.doneJumping` the players whose slot has ended, in order. Both are public and empty again in the next turn. After each jump `turn.landingShip` names the ship until its player chooses where it ends up (E04-S03); it's public and null when no ship waits. From Trading on, `turn.tradingQueue` lists the goods still to resolve, every good at every system when Trading starts, by system in map order then good, and `turn.resolvedGoods` the ones resolved, in order (E05-S01). Both are public and empty before Trading; the first player in `turn.initiative` orders and resolves them. `turn.resolution` is the good resolving now, or the last one once it has finished, and null before the first Resolve next (E05-S02). It's public: `offers` are every offer for that good at that system, disclosed when it starts resolving, in the order placed, with the Dictator's last if they placed one (`type` is `BUY` or `SELL`). `dictator` is the playerId of that good's Dictator at that system, or null; `awaitingDictator` is the same playerId while they still decide (R38), else null; `finished` is whether nothing is left to decide. The next good can't start until it's `true`. `startingCounter` is the good's S/D plus a 2d6 roll, null until the counter starts, which is once nobody is asked: at Resolve next with no Dictator, else after the Dictator's decision (E05-S03, R34, R38). `trades` are the offers the counter reached, in order: whose (`playerId`), `BUY` or `SELL`, the offer's price, `marketMax` (the most units the market allowed when the counter reached it) and the units its player traded (E05-S04). `units` is 0 when that player had nothing they could trade (S04-5: no money for a unit, or none of the good in their ships in port there) and acknowledged it; why is never sent (R29). `awaitingTrade` is the offer whose player the game waits for, with `maxUnits` the most the market allows, else null (public, D09); that player's own max after their money and cargo is `you.tradeMax` (0 when they can trade nothing), null for everyone else and whenever nobody waits on them. Before E05-S04 each offer traded the most it allowed at once, and no money or cargo moved. With the counter, `log` gains "{System} {GOODS}: market +3 → buyers first" (or "market −2 → sellers first") when it starts, one "{corporation} could buy up to 12 u: bought 10 u at 13 HT each, paid 130 HT" / "could sell up to … sold … received …" / "could buy up to 3 u: bought nothing" per trade as it's made, then "No one else can trade at {System} {GOODS}" once it's over, or "No one can trade at {System} {GOODS}" when no unit traded. E05-S05: `startPrice` is the good's price when it started resolving, which every max uses; once no offer can trade, `newPrice` is the start price plus the price modifier of the counter's final position, clamped to 1–20 (R35), else null, and `log` gains "{GOODS} price at {System}: 11 → 10 HT" right after the end line, even when nobody traded. From then on `board`'s `price` for that good is the new one: `board` carries this game's prices, which start at the board's and change only this way (the `indicator` never changes). `wholesalers` are who the wholesale step asks, fixed when the good starts resolving: its Wholesalers there without an offer for it, and its Dictator, in initiative order (R37). Once `newPrice` is set, `awaitingWholesaler` is the next of them who hasn't answered, else null; `wholesales` are the answers, in order: `role` `Wholesaler` or `Dictator`, `type` `BUY`, `SELL` or null for a pass, `units` (0 for a pass) and `price` (the new price). Each is logged: "{corporation} (Wholesaler) bought 3 u at 10 HT each, paid 30 HT", "… (Dictator) passed on wholesale". `you.wholesaleMax` is the most the caller may buy and sell (up to 5 u, after their money and the cargo in their ships in port there) while the wholesale step waits for them, else null (R29). E05-S06: a trade of 6 units or more rolls 2d6 for its player's market position for that good at that system (R43), unless they're its Dictator already: `positionRoll` is null for any other trade, else `roll`, `promotedTo` (the tier they now hold, one up from the one they held, or null when the roll was above the units traded) and `demoted` (the playerId of the Dictator it replaced, who is `WHOLESALER` now). `log` gains, right after that trade's line, "{corporation} traded 7 u — rolled 5: now Wholesaler of ISO at Mu Herculis" ("…; {corporation} is demoted to Wholesaler" for a demotion) or "… rolled 9: no change". The change is in `players[].marketPositions` at once, public to everyone. It changes nothing in the rest of that turn: each good resolves once a turn, and its Dictator and the Wholesalers asked are fixed when it starts. `log` is the game's public events, oldest first; each `turn` is the turn it happened in, which the Game log screen (s04) groups by (E03-S06). It never carries an offer, a bid, money or anything else confidential (R17, R29). It changed from `[string]` in E03-S06, with `index.html` updated in the same PR. **Players are named by id, never by email** (2026-11-17): `players[].id`, `creatorId`, `you.id` and every `playerId` above are `p1`, `p2`, … in join order (`p1` is the creator), fixed for the life of the game and meaningless outside it (`PlayerIds`). No response carries any player's email address, the caller's own included; before this change these fields were `email`, `creatorEmail` and `playerEmail` and held email addresses, with `index.html` and `static/js/*` updated in the same commit. E09 (2026-11-17): each `you.ships` entry also has `crewClass` (`A`–`D`), `saleValue` (what selling it pays), `canRefit` (whether it can be refitted now: in the yard, or in port at a shipyard system) and `leavesYardOnTurn` (the turn whose Investment it leaves the yard in, or null), and each of its `modules` an `id` (its `Module` constant) and a `resaleValue` (what removing one pays back); `you.invest.shipyard` lists what can be bought: the three shipyards, the civilian hulls and modules with their prices (R56: no military ones), each crew class's price per crew member, and `freeNames`, the suggested names no ship in the game has yet (R62). In Ship-jumps, a player with no ship able to jump (all in the yard, or none) has their slot end at once, and `log` gains "{corporation} has no ship to jump" (R64); a ship in the yard is never a landing choice, a jump, a Collect destination, a cargo move or presence at its system. Jump chance (R68, 2026-11-17): each `you.ships` entry also has `jumpChances`, `{ STAR_SYSTEM: { target, percent } }` for every system but its own, where a 2d6 roll of `target` or less makes the jump and `percent` is that chance rounded to a whole percent (100 from a target of 12). A jump now rolls 2d6: on success `log` reads "Jump: {corporation} — {ship} → {System} (rolled N)" and `turn.landingShip` names the ship as before; on failure the ship stays where it was, its name is in `turn.jumpedShips` with `turn.landingShip` null, and `log` reads "Jump: {corporation} — {ship} failed to jump to {System} (rolled N) and stays at {System}". Additive: no field was removed or renamed.

- `status` is `LOBBY`, `RUNNING` or `FINISHED`; a new game is `LOBBY` with `turn: null`, empty `log`, no ships and 0 money. The start (E02-S05) sets 300 HT, two ships at Ports and `turn: { number: 1, phase: BIDDING }`, and adds two log lines under turn 1. Phases then run Bidding → Ship-jumps → Trading → Investment → the next turn's Bidding; after the last turn's Investment `status` is `FINISHED` and `turn` keeps the last turn (E03-S01, E06-S01). Trading ends in the same request as the answer that finishes its last good, whichever endpoint that is (E05-S07): `log` gains "All goods resolved" under the turn, and `turn.phase` is `INVESTMENT` (E06-S01). Investment ends in the same request as the last player's `/investment/done`: unless it was the last turn (`turns`), `log` gains "Turn {n} of {turns} starts with Bidding; turn {n−1}'s offers have expired" under the new turn, whose `turn` is a fresh Bidding (no resolution, empty queues, empty `you.offers`, empty `doneInvesting`). After the last turn, `log` instead ends with "Game over: {corporation} wins with 2,310 HT" ("{a} and {b} win with …" for a shared win), and `result` is set (E05-S08): every player's final money, most first (cash only, R39), and the emails of the players with the most, several when tied. It is the only place another player's money appears, and only once `status` is `FINISHED` (the R29 exception); it's null before. Every action on a finished game is a `409` "This game is over".
- Games are stored in DynamoDB and survive a server restart (E02-S03); see §7 for the stored shape.
- `logOffset` (a number, beside `log`) is 0 on every answer except a poll sent with `logAfter`; every other endpoint answers with the whole log. The statuses above come from one place, `GameExceptionAdvice`: `404` no such game, `403` not a player or not the creator, `400` a request the player can correct, `409` out of turn, after the phase closed or in the wrong state.
- **Breaking change**: renaming or removing a field above; changing a status code; changing the `status` or `phase` values; rewording "Bidding has closed", which the game screens show as is; rewording a join or poll `403`/`404`/`409` message, which E02-S05's lobby screen shows as is; letting the poll return anything to a non-player (A05); sending any player's email address in any response; putting any player's money, cargo, offers or bid outside `you` (R29, S02-7, R17); rewording an offer or bid `400` message, which the forms show as is.
- **In-repo consumers**: `static/index.html` (s11 create, s12 lobby, the game view) through `static/js/game.js`, `static/js/board.js`, `static/js/cargo.js` (the Move goods panel, E08-S02, which shows `/cargo/moves`' `400` messages as is) and `static/js/trading.js` (s03, E05-S01), which read every field above and shows the `403`/`404`/`409` messages as is.

- Table `star-trader-games` (`DYNAMODB_TABLE_NAME`), on-demand billing, no secondary index. In real AWS it's provisioned outside the app.
- **Additive change** (a new attribute, a new field in a player map): safe once its item class defaults it when reading an older item.
- **Breaking change**: renaming or removing an attribute, changing its type or the meaning of a value (including renaming a `StarSystem`, `ShipLocation`, `GameStatus`, `TurnPhase`, `Goods`, `MarketTier` or `OfferType` constant, since they're stored by name), changing the key. Needs a migration of stored items, or — before any game worth keeping exists — an explicit note in the PR that local data must be cleared (`docker compose down -v`).
- **Log items** share the table, one per game per turn (`LogTurnItem`): `id` is `log#{gameId}#{turn}`, `turn` is N, and `entries` is an L of `{ turn: N, text: S }` (`LogEntryItem`), that turn's public events in the order they happened. The log grows with every good resolved, and inside the game item a long game would pass DynamoDB's 400 KB limit for one item. A change writes the game item and the log items of the turns it added lines to in one transaction, conditional on the game item's `version`; reading a game reads its item and then the log items `logTurns` lists. Changing how the id is built, or deleting a log item a game lists, loses that game's log (the read fails loudly rather than show a log with a hole).
- **Sessions** share the table, one item per login session (`login/adapter/dynamodb/SessionItem`): `id` is `session#` plus the SHA-256 (hex) of the session token, so the token itself is never stored; `playerName`, `corporationName` and `email` are S. Changing how the id is derived from the token signs every player out, so it needs the same care as changing the key.
- **Required path**: change the type's item class (`GameItem`, `LogTurnItem`, `PlayerItem`, `ShipItem`, `WarehouseItem`, `FactoryItem`, `MarketPositionItem`, `TurnItem`, `OfferItem`, `InitiativeBidItem`, `TurnOrderPickItem`, `MarketGoodItem`, `LogEntryItem`, `SessionItem`) and its round-trip test together (engineering standards §12), and state the change in the PR body.

## Confidential-data authorization

The session→player→game check from product-brief assumption A05 exists: every game endpoint resolves the caller from their session, a caller who isn't in the game gets `403` with no game data (`GamePollingService`, and `Game.playerOf` on every action), and private state travels only under `you`, built for the caller (§6). Loosening any of it is always a blocker-severity review finding (see `CODE_REVIEW.md`), never a plain compatibility note.

## Required path for any breaking change, in general

1. State the break explicitly in the PR body (what surface, what changes, who/what consumes it).
2. Update every in-repo consumer in the same PR (currently: the static frontend).
3. If the surface is tied to a product-brief business rule or decision, add a superseding entry there per `SDLC.md`'s "Amending this process" / the product brief's own change-control table.
4. Prefer additive changes (new field, new endpoint) over renaming/removing while any real consumer might exist.
